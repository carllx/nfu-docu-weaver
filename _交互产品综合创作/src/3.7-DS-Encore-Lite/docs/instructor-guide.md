# Encore-Lite 讲师备课指南

## 📌 课程定位与目标

### 核心理念
这不是一门"工具使用"课，而是一门"系统思维"课。我们通过 Figma 和 H5 这两个载体，教授的是**协议驱动的设计系统方法论**。

### 教学目标（SMART原则）
- **具体 (Specific):** 学生能构建一个包含两级代币、3个组件、支持主题切换的 H5 页面
- **可衡量 (Measurable):** 90%学生能通过 5 个检查点，提交完整的代码仓库
- **可达成 (Achievable):** 3-4小时完成，适合本科高年级或研究生
- **相关性 (Relevant):** 与真实行业实践（Spotify Encore）直接关联
- **有时限 (Time-bound):** 单次课程或工作坊形式

## 🎓 分模块教学要点

### 第一部分：理论导入 (30分钟)

#### 开场技巧
**❌ 不要这样开场：**
> "今天我们要学习设计系统..."

**✅ 推荐开场：**
> "大家用过 Spotify 吗？（等待举手）有没有注意到，无论你在手机、电脑还是网页上，它的绿色按钮总是一模一样？（展示截图）今天我们就来学习这背后的秘密..."

#### 案例展示要点
1. **对比冲击：** 展示不一致的界面 vs 一致的界面
2. **痛点共鸣：** 讲述设计师和开发者的真实困扰
3. **价值锚定：** "这套方法可以节省50%的沟通时间"

#### 概念讲解节奏
- **5分钟：** 设计代币是什么（用"颜料管"类比）
- **5分钟：** 两级代币架构（现场画图）
- **5分钟：** 协议契约（展示真实的 SemVer 案例）
- **15分钟：** Q&A + 案例讨论

**💡 教学提示：**
- 避免一次性灌输太多术语
- 每个概念都要有视觉化的例子
- 鼓励学生提问，记录高频疑问

### 第二部分：Figma 实战 (60分钟)

#### 教学模式切换
```
前20分钟（代币定义）：
├─ 讲师演示 (70%) + 学生跟随 (30%)
├─ 节奏：慢速，每个操作都暂停确认
└─ 检查方式：举手示意，巡视屏幕

中20分钟（Button组件）：
├─ 讲师演示 (50%) + 学生跟随 (50%)
├─ 节奏：中速，关键步骤暂停
└─ 检查方式：让学生展示成果

后20分钟（复杂组件）：
├─ 讲师引导 (30%) + 学生独立 (70%)
├─ 节奏：快速引导，提供结构参考
└─ 检查方式：同伴互查 + 讲师抽查
```

#### 常见卡点与解决方案

**卡点 1：变量 Modes 不显示**
- **原因：** 没有先创建 Collection
- **解决：** 强调"Collection → Modes → Variables"的顺序

**卡点 2：语义代币无法引用原始代币**
- **原因：** 两个代币类型不匹配（Color vs Number）
- **解决：** 提前讲解代币类型的概念

**卡点 3：组件变体创建失败**
- **原因：** 没有先转为 Component
- **解决：** 明确步骤：Frame → Component → Variant

**卡点 4：Auto Layout 间距不生效**
- **原因：** 选中了错误的图层
- **解决：** 强调"Auto Layout 只作用于父容器"

#### 巡视指导技巧
- **每5分钟巡视一次全班**
- **发现共性问题 → 暂停全班讲解**
- **发现个性问题 → 记录后单独辅导**
- **鼓励快速的学生帮助慢速的学生**

### 第三部分：H5 实现 (60分钟)

#### 代码演示技巧

**屏幕布局建议：**
```
┌─────────────────────────────────┐
│  VS Code (左侧 70%)              │
│  ├─ style.css (主要编辑)         │
│  └─ index.html (偶尔切换)        │
├─────────────────────────────────┤
│  浏览器 (右侧 30%)               │
│  └─ Live Server 实时预览          │
└─────────────────────────────────┘
```

**编码节奏控制：**
- **代币定义阶段：** 逐行敲代码，边敲边讲解
- **组件样式阶段：** 提供代码片段，讲解关键部分
- **HTML结构阶段：** 学生独立完成，讲师提供框架

#### 关键概念强调点

**1. CSS 变量的两层架构 (15:00-15:05，重复3次):**
```css
/* 第一层：Primitives（颜料） */
:root {
  --primitive-green-400: #1ED760;
}

/* 第二层：Semantics（用途） */
:root {
  --color-interactive-primary: var(--primitive-green-400);
}

/* 使用时只用语义代币 */
.button {
  background: var(--color-interactive-primary); /* ✅ 正确 */
  background: var(--primitive-green-400);       /* ❌ 错误 */
  background: #1ED760;                          /* ❌❌ 严重错误 */
}
```

**2. BEM 命名的"为什么" (重点讲解):**
```
不是为了"好看"，而是为了：
1. 降低 CSS 优先级冲突
2. 组件可以安全地复制到任何项目
3. 新人可以快速理解代码结构
```

**3. "零硬编码"原则的执行 (巡视时重点检查):**
```css
/* 学生常犯错误 */
.button {
  padding: 16px;  /* ❌ 硬编码 */
  padding: var(--spacing-m); /* ✅ 正确 */
}
```

#### 调试指导
**常见错误 Top 5：**

1. **CSS 变量名拼写错误**
   - 症状：样式不生效
   - 检查：DevTools → Computed → 查看 `var()` 是否解析
   - 修复：对比 `:root` 中的定义

2. **忘记引入 CSS 文件**
   - 症状：页面无样式
   - 检查：HTML 中的 `<link>` 标签
   - 修复：添加 `<link rel="stylesheet" href="style.css">`

3. **JavaScript 选择器错误**
   - 症状：主题切换不工作
   - 检查：Console 中是否有错误
   - 修复：确认 `getElementById` 的参数

4. **Flexbox 对齐问题**
   - 症状：元素位置不对
   - 检查：是否设置了 `display: flex`
   - 修复：复习 Flexbox 的 justify-content / align-items

5. **响应式媒体查询不生效**
   - 症状：小屏幕布局不变
   - 检查：是否有 `<meta name="viewport">` 标签
   - 修复：添加 viewport meta 标签

### 第四部分：增强与优化 (45分钟)

#### 响应式设计的教学重点

**不要只讲"怎么做"，更要讲"为什么这样做"：**

```css
/* 示例讲解 */
@media (max-width: 768px) {
  .playlist-header {
    flex-direction: column; /* 为什么用 column？ */
    text-align: center;      /* 为什么居中？ */
  }
}
```

**讲解框架：**
> "在小屏幕上，横向空间有限，如果还用 row 布局，封面和文字会被挤压。
> 改为 column 后，内容垂直排列，每个元素都能有足够的空间。
> 居中对齐是因为这样视觉上更稳定，用户的视线不用左右移动。"

#### 可访问性的深度讲解

**用真实场景引导思考：**

1. **键盘导航：**
   > "想象一下，如果你的手受伤了，只能用键盘，你能操作这个页面吗？"
   
2. **屏幕阅读器：**
   > "视障用户会用屏幕阅读器，如果你的按钮只有一个图标没有文字，软件会读出什么？"
   
3. **颜色对比度：**
   > "有8%的男性有不同程度的色盲，如果对比度太低，他们可能根本看不到你的按钮。"

**工具实操演示：**
- 打开 Chrome DevTools → Lighthouse → Accessibility
- 现场跑一次审计，展示如何读报告
- 修复一个问题，重新跑审计，展示分数提升

### 第五部分：契约验证 (30分钟)

#### 契约文档的"仪式感"

**重要提示：** 不要让学生觉得这只是"写个文档"，要营造出"签署协议"的庄重感。

**教学话术：**
> "现在我们要做一件很重要的事情——为我们的设计系统'立法'。
> 在真实团队中，这份文档就像是团队的宪法，所有人都要遵守。
> 如果有人想打破规则，必须走正式的变更流程。"

#### 变更演练的"角色扮演"

**场景设定：**
```
角色分配：
├─ 设计师（提出变更）
├─ 开发者（评估影响）
├─ 产品经理（决策批准）
└─ QA（验证测试）
```

**演练脚本（非破坏性变更）：**
```
设计师: "我们需要添加一个新的边框颜色，用于表单。"
开发者: "这是新增代币，属于 MINOR 变更，不会影响现有组件。"
产品经理: "批准，记录到 v0.2.0 的 Changelog。"
QA: "我来验证一下新代币在两个主题下都显示正常。"
```

**演练脚本（破坏性变更）：**
```
设计师: "我觉得 'interactive' 这个名字不够准确，想改成 'brand'。"
开发者: "等等，这会影响 3 个组件，需要重新测试。这是 MAJOR 变更！"
产品经理: "我们需要评估风险。这个变更能带来多大价值？"
设计师: "命名更准确，新人更容易理解。"
产品经理: "好，批准。但需要写详细的迁移指南，并通知所有开发者。"
QA: "我来跑完整的测试矩阵，确保没有遗漏。"
```

#### 多样性测试的"质量门"意识

**教学话术：**
> "在真实项目中，这些测试就是'质量门'（Quality Gate）。
> 如果有任何一项不通过，代码就不能合并到主分支。
> 这不是为了为难谁，而是为了保证产品质量的底线。"

**测试演示顺序：**
1. **先展示"通过"的状态** → 建立信心
2. **故意制造一个"失败"** → 展示如何修复
3. **重新测试"通过"** → 强化"测试-修复-验证"循环

## 🚨 突发情况应对

### 技术故障

**情况 1：校园网络中断**
- **预案：** 提前下载所有资源到本地
- **应对：** 开启手机热点，学生下载离线包
- **备选：** 如果无法联网，使用本地 HTML 演示

**情况 2：学生电脑性能差，Figma 卡顿**
- **预案：** 建议关闭其他应用
- **应对：** 降低 Figma 文件的复杂度（减少图层数）
- **备选：** 使用 Figma 浏览器版本（比桌面端更流畅）

**情况 3：Live Server 无法启动**
- **预案：** 提前测试所有学生的环境
- **应对：** 使用 VS Code 的 "Open with Browser" 功能
- **备选：** 手动刷新浏览器

### 教学节奏问题

**情况 1：进度严重落后（超过15分钟）**
- **诊断：** 快速调查是个别学生还是全班问题
- **应对：**
  - 全班问题 → 简化后续内容，跳过"增强"部分
  - 个别问题 → 安排助教/快速学生一对一辅导
  - 提供"半成品文件"让落后学生追赶进度

**情况 2：进度超前（提前30分钟完成）**
- **利用：** 立即启动扩展挑战
- **深化：** 讲解进阶概念（容器查询、CSS Layers）
- **拓展：** 讨论真实项目中的复杂场景

**情况 3：学生参与度低，课堂沉闷**
- **唤醒：** 插入互动环节（两人一组互相检查）
- **激励：** 展示优秀学生的成果，给予表扬
- **调整：** 增加实战时间，减少讲解时间

### 内容理解问题

**情况 1：学生对"协议"概念理解困难**
- **换个类比：** "就像交通规则，红灯停绿灯行"
- **具体案例：** "如果没有协议，北京的开发者用 primary，上海的用 main，乱套了"
- **视觉化：** 画图展示有协议 vs 无协议的对比

**情况 2：学生混淆"原始代币"和"语义代币"**
- **强化类比：** 
  - 原始 = 超市的原料（面粉、鸡蛋）
  - 语义 = 菜单上的菜名（蛋糕、面包）
  - 我们点餐时说"来一份蛋糕"（语义），而不是"来500g面粉+2个鸡蛋"（原始）

**情况 3：学生不理解为什么要这么"麻烦"**
- **反问：** "如果产品说'把所有蓝色改成绿色'，你愿意手动改500个文件，还是改1个变量？"
- **算账：** "建立系统花1小时，省后续10小时，划算吗？"
- **展示：** 现场演示主题切换的威力（1秒切换 vs 手动改需要1小时）

## 🎤 讲师话术库

### 开场语 (选择一个)

**版本 A - 痛点共鸣型：**
> "在座有多少人遇到过这种情况：辛辛苦苦做的设计，开发实现后完全走样？或者改一个颜色，要手动修改100个地方？（等待回应）今天我们就来彻底解决这个问题。"

**版本 B - 好奇心驱动型：**
> "大家知道 Spotify 的绿色有多少个吗？（停顿）答案是1个。但它出现在1000+个组件里，却永远保持一致。这背后的魔法，就是我们今天要学的设计系统。"

**版本 C - 价值锚定型：**
> "今天的课程，可能会改变你未来5年的工作方式。学会它，你可以让团队效率提升50%，让产品质量提升一个档次。我知道3小时很长，但相信我，绝对值得。"

### 过渡语 (连接各部分)

**从理论到实践：**
> "好，理论讲完了。现在是最激动人心的部分——我们要亲手构建一个设计系统。准备好了吗？"

**从 Figma 到代码：**
> "恭喜大家完成了 Figma 部分！现在我们要做一件魔法般的事情——把这些设计'变成'真实可用的网页。"

**从基础到进阶：**
> "现在我们的页面已经能工作了，但还只是'能用'。接下来我们要让它变成'好用'——响应式、可访问、高性能。"

### 鼓励语 (在学生遇到困难时)

**卡住时：**
> "没关系，这个地方确实有点绕。我第一次学的时候也卡了半小时。我们一起来看看问题在哪儿..."

**出错时：**
> "太好了，你发现了一个 bug！在真实项目中，发现bug越早，修复成本越低。这就是测试的价值。"

**落后时：**
> "我看到你还在第X步，别着急。我待会儿会给你一个半成品文件，让你能跟上大部队。现在先继续听，理解原理更重要。"

### 收尾语

**总结型：**
> "今天我们从零开始，构建了一个完整的设计系统。虽然它只有3个组件，但你们学到的思维方式，足以应对3000个组件的系统。记住核心：协议、分层、契约、测试。"

**激励型：**
> "你们现在掌握的技能，很多工作3年的设计师和开发者都不具备。好好利用它，它会成为你们的核心竞争力。"

**行动号召型：**
> "课程结束不是终点，而是起点。回去后，试着在你的项目中应用这套方法。一个月后，来告诉我你的收获。我期待你们的好消息！"
