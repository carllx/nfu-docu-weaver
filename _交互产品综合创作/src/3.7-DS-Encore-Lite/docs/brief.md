**项目简报：Encore-Lite 设计系统教学案例**

**TO:** 项目负责人 **FROM:** Analyst Mary **DATE:** 2025年10月17日 **SUBJECT:** 关于 "Figma x H5" 教学案例从初始构想到最终方案的演化路径与目标总结 (v2.0)

### 1. 项目背景与初始目标

项目启动于一个明确但基础的需求：**如何将 Figma 中设计的组件，以遵循原子设计理念的方式，映射到传统的 H5 (HTML/CSS) 代码中**。初始讨论聚焦于解决在无前端框架环境下，如何实现 UI 组件的结构对应与样式复用。

### 2. 核心问题演化路径

在讨论过程中，我们的核心问题经历了一系列深刻的、由表及里的演化，最终将一个简单的“映射任务”提升为一个全面的“社会技术系统工程”教学案例。

- **2.1 从“静态映射”到“可复用组件”**
    
    - **演化:** 意识到简单的视觉对应不足以体现组件化价值，**“复用”**成为核心议题。
        
- **2.2 从“通用案例”到“品牌系统启发 (Encore-Lite)”**
    
    - **演化:** 引入行业标杆 **Spotify** 作为灵感，但做出关键决策：**学习其设计系统 “Encore” 的组织法则，而非其视觉资产**。案例被重新定义为 **“Encore-Lite”**。
        
- **2.3 从“变量列表”到“语义化决策”**
    
    - **演化:** 引入**认知负荷理论**，我们升级为建立**两级代币架构（核心 → 语义）**和**“选择架构/决策树”**，将抽象的数字转化为有明确使用场景的“通用语言”。
        
- **2.4 从“设计规范”到“可执行契约”**
    
    - **演化:** 引入**边界客体**与**行动者网络理论**，我们将设计系统的核心提升为一份**机器可读、可自动验证的“契约”**。`tokens.json` + JSON Schema 成为连接所有行动者的**唯一真理之源 (Single Source of Truth)**。
        
- **2.5 从“孤立的技术”到“被治理的社会技术系统”**
    
    - **演化:** 引入 **GOV.UK 治理范式**与**康威定律**的思考，我们认识到技术契约必须有**社会契约**来支撑。课程正式引入**治理轨道**，包括角色与职责（RACI）、版本语义（SemVer）和变更审议流程（RFC），将设计系统视为一个需要组织流程保障的社会技术系统。
        
- **2.6 从“视觉测试”到“协议化的契约剧场”**
    
    - **演化:** 引入**设计即协议**与**批判性工程**思想，我们将测试从简单的“视觉比对”升级为对**“契约不变式 (Invariants)”**的严格验证。**“契约剧场”**成为强制性的质量门，覆盖可访问性、布局、性能和变量引用的不可破坏条件。
        

### 3. 最终确定的项目目标

**我们的最终目标是：** 在一天（或一周）的课程内，引导学生完成一个以 **“Encore-Lite”** 为主题的微型设计系统工程实践，产出一个**以设计代币为唯一真源、经协议化契约验证、具备组织治理与内在韧性**的 H5 页面。

- **核心产出物:**
    
    1. 一个遵循两级代Git币架构的 **Figma 组件库**。
        
    2. 一个**可治理的代码库**，包含 `/tokens` (契约), `/governance` (治理), `/tests` (不变式)。
        
    3. 一个完全由代币驱动、无硬编码、通过**“契约剧场”和“必要多样性”测试矩阵**的 H5 页面。
        
- **核心教学方法论:**
    
    - **语义化决策:** 通过“选择架构”降低认知负荷。
        
    - **契约驱动开发:** 强调“唯一真理之源”与自动化验证。
        
    - **内在韧性设计:** 强制使用 CSS 逻辑属性、容器查询等现代布局技术。
        
    - **治理即代码:** 将组织流程（RACI, RFC）文档化，与代码一同接受版本管理。
        

### 4. 关键决策与理由

- **为什么是 "Encore-Lite" 而非 "Spotify 克隆"?**
    
    - **理由:** 为了将学生的注意力从“品牌资产的模仿”转移到“可迁移的系统方法论”上。我们学习的是 Spotify 设计系统背后的**组织法则**，而非其视觉表皮。
        
- **为什么我们的架构优于简单的文件分离?**
    
    - **理由:** 简单的文件分离是一种优秀的**代码组织方式**，但我们的架构是一种更高级的**系统工程方法**。通过将 `tokens.json` 确立为跨平台的“唯一真理之源”，并为其配备治理和契约测试，我们从根本上解决了设计与代码的长期同步问题。
