**项目简报：Encore-Lite 设计系统教学案例**

TO: 项目负责人

FROM: Analyst Mary

DATE: 2025年10月17日

SUBJECT: 关于 "Figma x H5" 教学案例从初始构想到最终方案的演化路径与目标总结

### 1. 项目背景与初始目标

项目启动于一个明确但基础的需求：**如何将 Figma 中设计的组件，以遵循原子设计理念的方式，映射到传统的 H5 (HTML/CSS) 代码中**。初始讨论聚焦于解决在无前端框架环境下，如何实现 UI 组件的结构对应与样式复用。

### 2. 核心问题演化路径

在讨论过程中，我们的核心问题经历了一系列深刻的、由表及里的演化，最终将一个简单的“映射任务”提升为一个全面的“系统工程”教学案例。

- **2.1 从“静态映射”到“可复用组件”**
    
    - **起点:** 如何让代码“长得像”Figma 设计。
        
    - **演化:** 意识到简单的视觉对应不足以体现组件化价值，**“复用”**成为核心议题。为此，我们将教学案例从缺乏复用场景的“用户评论”组件，升级为天然需要重复与变体的**“定价卡片”**组件。
        
- **2.2 从“通用案例”到“品牌系统启发 (Encore-Lite)”**
    
    - **起点:** 使用一个通用的、虚构的案例。
        
    - **演化:** 为了增加案例的真实性与深度，我们引入了行业标杆 **Spotify**。但为了避免学生陷入“品牌复刻”的细节陷阱，我们做出了关键决策：**学习其设计系统 “Encore” 的组织法则，而非其视觉资产**。案例被重新定义为 **“Encore-Lite”**，一个去品牌化的、以系统方法为核心的教学载体。
        
- **2.3 从“变量列表”到“语义化决策”**
    
    - **起点:** 为学生提供一套数字化的设计变量（如 `spacing-8`, `spacing-16`）。
        
    - **演化:** 引入**认知负荷理论**，我们意识到无上下文的变量列表会增加而非降低设计复杂性。方案升级为建立**两级代币架构（核心 → 语义）**和**“选择架构/决策树”**，将抽象的数字转化为有明确使用场景的“通用语言”（如 `space-container`, `color-text-primary`）。
        
- **2.4 从“设计规范”到“可执行契约”**
    
    - **起点:** 将设计系统视为一份供人阅读和遵守的文档。
        
    - **演化:** 引入**边界客体、行动者网络理论及 GOV.UK 治理范式**，我们将设计系统的核心提升为一份**机器可读、可自动验证的“契约”**。**`tokens.json` + JSON Schema** 成为连接所有行动者（Figma, 开发者, CI/CD）的**唯一真理之源 (Single Source of Truth)**。版本治理 (SemVer)、消费者驱动的契约测试、机器可读的例外契约等工程化实践被正式纳入课程。
        
- **2.5 从“理想环境”到“多样性韧性”**
    
    - **起点:** 在单一、理想的上下文（单主题、单语言、单视口）中构建和测试组件。
        
    - **演化:** 意识到系统的真正价值在于其在真实、复杂环境中的稳定性，我们引入了**“必要多样性”测试矩阵**。要求组件必须在**多主题（亮/暗/高对比）、多脚本（拉丁/RTL/CJK）、多密度**的环境下保持内在韧性，并通过自动化测试进行验证。
        

### 3. 最终确定的项目目标

**我们的最终目标是：** 在一天（或一周）的课程内，引导学生完成一个以 **“Encore-Lite”** 为主题的微型设计系统工程实践，产出一个**以设计代币为唯一真源、经契约测试、具备内在韧性与初步治理能力**的 H5 页面。

- **核心产出物:**
    
    1. 一个遵循两级代币架构的 **Figma 组件库**。
        
    2. 一套机器可读的**设计契约** (`tokens.json` + `tokens.schema.json`)。
        
    3. 一个完全由代币驱动、无硬编码、通过**多样性测试**的 H5 页面。
        
- **核心教学方法论:**
    
    - **语义化决策:** 通过“选择架构”降低认知负荷。
        
    - **契约驱动开发:** 强调“唯一真理之源”与自动化验证。
        
    - **内在韧性设计:** 强制使用 CSS 逻辑属性、容器查询等现代布局技术。
        
    - **每日构建，每日验证:** 将复杂的系统工程分解为可管理的每日交付成果。
        

### 4. 关键决策与理由

- **为什么是 "Encore-Lite" 而非 "Spotify 克隆"?**
    
    - **理由:** 为了将学生的注意力从“品牌资产的模仿”转移到“可迁移的系统方法论”上。我们学习的是 Spotify 设计系统背后的**组织法则**，而非其视觉表皮。
        
- **为什么我们的架构优于简单的文件分离?**
    
    - **理由:** 简单的文件分离（如 `globals.css`, `style.css`）是一种优秀的**代码组织方式**，但我们的架构是一种更高级的**系统工程方法**。通过将 `tokens.json` 确立为跨平台的“唯一真理之源”，我们从根本上解决了设计与代码的长期同步问题，并为自动化、演化和治理奠定了基础。
