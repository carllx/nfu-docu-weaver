# 智能体课程设计讨论材料

## 原始材料
- **材料类型**：长篇系统架构与工作流设计对话记录 (ChatGPT transcript)。
- **对话参与者**：用户 (User) 与 LLM (ChatGPT)。
- **时间范围**：2026-07-26 21:44:37 至 23:16:58。
- **原始文件位置**：`Projects/智能体课程设计MVP实验/ChatGPT_架构讨论实录.md`
- **外部来源链接**：[ChatGPT 会话记录](https://chatgpt.com/c/6a660b97-93f4-83ea-9f0d-1f7bd84852a9)

## 最初目标
探索如何利用 `notebooklm-py` 库，在 Antigravity IDE 中组织多个 Sub Agent 进行轮番讨论，以 NotebookLM 为证据库，针对用户提供的大致方向和教材生成可靠的课程大纲。

## 用户的核心判断
1. **防止模型幻觉**：不能让 Agent “假装”是作者自由发挥，而必须强制其基于选定的来源发言。
2. **人类不可替代**：Agent 只能梳理知识与发现张力，“这东西能不能教”、“适不适合现在的学生”必须由人类讲师裁定。
3. **反对过度工程化**：在尚未验证核心框架是否有用之前，拒绝过早引入复杂的 Python 状态机、多模型后端适配和繁琐的 JSON/YAML Schema，倾向于先跑通“最小可行框架”。

## 讨论过的方案
在系统设计阶段，曾针对架构进行了多轮详细的 A/B/C 决策权衡，涵盖了：
- **取证方式**：NotebookLM 负责日常，Local LLM 负责高危审计。
- **Agent 状态**：固定角色身份，但每轮必须重新取证，不依赖历史记录作证。
- **会议结构**：每本书一个代表，另设主控和公共审查角色。
- **人机干预**：固定关卡 + 异常情况触发（如发生死循环或教材冲突）。
- **停止条件**：多条件收敛判定（非简单的固定轮数或强求共识）。
- **信息共享**：建立“结构化黑板”进行上下文分发，而非互相阅读全部聊天记录。

## 被放弃的方案及原因
- **完全自由的多 Agent 辩论**：被放弃。原因：调用量会指数增长，容易脱离原教材，且难以设定停止条件。
- **完全依赖 Python 脚本运行 Agent (Local LLM API 适配器)**：被放弃。原因：用户指出这会让系统变成一个晦涩的黑盒程序，超出了当前阶段的需要（属于过度工程化）。
- **长期的 Agent 记忆**：被放弃作为“证据来源”。原因：Agent 容易被历史聊天污染，将前几轮的妥协当成书本原意。
- **复杂的收敛状态机与本地目录管理**：被放弃。原因：在核心可行性被证明前，建立大量目录、账本和校验文件会增加不可靠性。

## 关键转折点
在深入设计了十几个微观架构决策（包括如何保存 blackboard、如何调用 LLM API）后，用户在 23:16:58 踩下刹车，指出当前设计**过于细致、复杂、具有局限性且超出人类理解范围**，要求退回到“最小可行框架（MVP）”。这一转折促成了最终“五步法”的诞生。

## 形成的方法原则
1. **隔离原则**：事实检索（NotebookLM）、架构综合（主控Agent）与价值取舍（人类）必须分离。
2. **证据要求**：Agent 不得脱离来源虚构教学活动，找不到证据必须弃权。
3. **MVP 原则**：先用极简的流程（提案 -> 批评 -> 综合 -> 人类验收）跑通。

## 实验与实际结果
用户后续实际执行了这一精简流程，并证实“成功生成了一个包含 4-6 个模块的课程大纲”，初步验证了该方向的可行性。

## 尚未解决的问题
- MVP 框架虽然轻量，但面对多达 10 本以上教材时，主控 Agent 的合成能力和上下文窗口是否能承受？
- 如何系统化地应对不同类型（理论、实践、案例）教材之间的深层冲突？
